# Pune flood geography pipeline

## Integrated sources and exact limits

`data/raw/pune_waterways.geojson` is an OpenStreetMap/Overpass snapshot with 213 valid WGS84 line features: 31 canals, 16 rivers, 129 streams, 30 drains and 7 ditches. Forty-six records carry culvert tags. The validator found no duplicate OSM IDs or failed geometries. `data/processed/pune_waterways_validation.json` records the source SHA256, snapshot timestamp, per-class counts, all zone indicators and any failures. These are mapped features; completeness, flow direction, cross-section, condition and drainage capacity are unknown.

From `backend`, run `python scripts/import_pune_waterways.py` to validate without writes. For a new database, apply migrations 001–006 in numeric order. The importer supports `--import-db` with server-side `DATABASE_URL` or `--import-supabase` with the existing server-side `SUPABASE_URL` and `SUPABASE_SECRET_KEY`. Both preserve OSM IDs, tags, attribution and EPSG:4326 MultiLineString geometry. Unique `(source_dataset, external_id)` keys skip existing lines. Zone indicators merge only mapped-distance, culvert-count and provenance fields, preserving WorldPop and terrain values. The REST route preflights all nine zone IDs and the required 006 columns before any writes. On 30 October 2026, 213 lines and nine mapped metrics were committed to the current Supabase project; readback found 213 unique IDs, and a second run inserted zero.

For an authoritative municipal line dataset, provide GeoJSON in EPSG:4326 with `properties.external_id`, `properties.waterway_class`, optional `name` and boolean `is_culvert`. Supply `--municipal-metadata metadata.json` containing `authority`, `dataset_id`, `licence`, ISO `capture_date`, and HTTPS `source_url`. Keep official attribution and source IDs. Municipal lines are stored under their own source namespace; importing them does not overwrite OSM-derived zone metrics. A municipality-provided line is treated as mapped geometry, not proof of working drainage capacity; independent hydraulic attributes need their own validation before use.

## Derived features and vulnerability

Each reproducible Pune analysis cell receives the metric distance from its centroid to the nearest mapped waterway and mapped drain/ditch, plus the count of culvert-tagged lines intersecting its polygon. UTM zone 43N is used for distances. All nine cells have both distance indicators; seven cells intersect at least one tagged culvert. These indicators **do not** populate the existing `drainage_index` capacity input and do not change the flood score. The dashboard displays their source and limitations.

`vulnerability-screening-v1` is a provisional 0–1 zone index with weighted components: population density (0.40, capped at 30,000 people/km²), flat terrain from mean slope (0.15, normalized over 0–10°), mapped hospital/school/emergency asset concentration (0.20, capped at 20 features), and sourced historical flood-exposure indicator (0.25). Available weights are renormalized. A score requires population plus two other independent domains; otherwise it is unavailable. This is a screening index, not calibrated physical loss, social vulnerability, flood probability, or evacuation priority. Run `python scripts/derive_vulnerability.py` with `DATABASE_URL` to inspect availability; add `--import-db` only after reviewing its report. The DEM slope is now persisted for all nine cells with supplied product metadata. No historical exposure dataset or vulnerability score has been stored.

## Verified historical event labels

Use the header-only [format example](../backend/examples/verified_flood_labels.csv). Every CSV row requires `event_id`, timezone-aware ISO `event_date`, `latitude`, `longitude`, `source`, `temporal_resolution_hours` (1–168), explicit `observed_flood_status` (`true`/`false` or `1`/`0`), `verification_reference`, and `observation_method`. An explicit negative means verified observation of no flood during that window; missing reports are never converted to negatives. Coordinates must map to exactly one analysis cell. Run `python scripts/import_verified_flood_labels.py --input path/to/verified_labels.csv` to validate; use `--import-db` only with reviewed evidence, migration 006 and `DATABASE_URL`. Inserts are idempotent by event ID. Labels are held server-side under RLS.

`python scripts/audit_flood_training_data.py` found zero verified positive or negative labels in `data/raw`. Its [audit](../ml/dataset_audit.json) keeps XGBoost training disabled. Even a future count threshold requires linkage to weather/terrain features available **before** each event, grouping related observations to avoid leakage, and chronological train/validation/test periods before training. With no valid labels, there is no XGBoost artifact, precision/recall/F1/PR-AUC/calibration evaluation, or SHAP explanation. The existing `flood-rainfall-index-v1` heuristic remains the active method and is never presented as a calibrated probability.
